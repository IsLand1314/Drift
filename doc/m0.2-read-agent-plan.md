# M0.2 Read Agent Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let Drift use one native `read_file` tool to answer a prompt about a workspace file through at most two OpenAI Compatible model requests.

**Architecture:** Extend `llm` so the provider can serialize tools and return an aggregated assistant message. Add a narrowly scoped `tool/read.go`, then put the two-turn decision logic in `agent.Run`; `app.Run` only wires CLI I/O, workspace root and the Agent together.

**Tech Stack:** Go 1.26+, standard library: `context`, `encoding/json`, `net/http`, `path/filepath`, `os`, `testing` and `httptest`.

**Spec:** [M0.2 Read Agent Loop Design](m0.2-read-agent-design.md)

## Global Constraints

- Use Go 1.26+ and no new dependencies.
- Only `read_file` exists; do not create a registry, generic tool interface, permission mode, session store, concurrency or extra tools.
- The task makes at most two provider requests and at most one tool call.
- Read only a regular workspace file; reject absolute paths, traversal, symlink escapes, directories and files over 128 KiB.
- Preserve `reasoning_content` from DeepSeek tool-call turns in the next request.
- stdout contains final model text; diagnostics remain on stderr; API keys remain environment-only.
- Commits use Chinese messages and `island` as author and committer; do not stage the pre-existing `README.en.md` deletion.

## Task 1: Expand the provider protocol and parse streamed Tool Calls

**Files:**

- Modify: `internal/llm/client.go`
- Modify: `internal/llm/openai/client.go`
- Modify: `internal/llm/openai/client_test.go`

**Interfaces:**

Consumes existing OpenAI Compatible POST/SSE client and text-stream tests.

Produces:

~~~go
type ToolDefinition struct {
    Type     string          `json:"type"`
    Function json.RawMessage `json:"function"`
}

type ToolCall struct {
    ID        string
    Type      string
    Name      string
    Arguments string
}

type Message struct {
    Role             string
    Content          string
    ToolCalls        []ToolCall
    ToolCallID       string
    ReasoningContent string
}

type StreamEvent struct {
    Text             string
    ReasoningContent string
    ToolCallDelta    *ToolCallDelta
}

type ToolCallDelta struct {
    Index     int
    ID        string
    Name      string
    Arguments string
}

type Completion struct {
    Assistant    Message
    FinishReason string
}

type Client interface {
    Stream(context.Context, Request, func(StreamEvent) error) (Completion, error)
}
~~~

- [ ] **Step 1: Write the failing streaming protocol test**

Create `TestStreamAggregatesToolCall`. Its `httptest.Server` sends three SSE events: the first supplies call ID `call_1`, name `read_file` and arguments `{"path":"REA`; the second appends `DME.md"}` and a `reasoning_content` fragment; the final event has `finish_reason:"tool_calls"` and `[DONE]`. Assert one completed call with raw arguments `{"path":"README.md"}`, preserved reasoning text, and a first request containing one function under `tools`.

- [ ] **Step 2: Run the focused test and verify it fails**

Run:

~~~powershell
go test ./internal/llm/openai -run TestStreamAggregatesToolCall -count=1
~~~

Expected: it fails to compile because the new completion and tool protocol does not exist.

- [ ] **Step 3: Change the shared contract and request wire format**

Add the exact shared types above. Add `Tools []ToolDefinition` to `Request`. In the OpenAI adapter, serialize a `ToolCall` as:

~~~json
{"id":"call_1","type":"function","function":{"name":"read_file","arguments":"{\"path\":\"README.md\"}"}}
~~~

Keep this nesting private to the OpenAI adapter; the rest of Drift uses `Name` and `Arguments`.

- [ ] **Step 4: Aggregate SSE deltas**

In `readStream` maintain `map[int]*ToolCall`, keyed by provider `delta.tool_calls[].index`. Fill empty ID/type/name fields, append argument fragments, text fragments and `reasoning_content` fragments. Save the last non-empty finish reason. Retain the existing 1 MiB event limit, `[DONE]` requirement, callback error propagation and service-body redaction.

- [ ] **Step 5: Add protocol regression cases**

Add direct `stop` text, two indexes, malformed raw function arguments, callback failure and `finish_reason:"length"` cases. The adapter preserves malformed arguments as a string; validation belongs to Task 2.

## Task 2: Implement bounded `read_file`

**Files:**

- Create: `internal/tool/read.go`
- Create: `internal/tool/read_test.go`

**Interfaces:**

Consumes `llm.ToolDefinition`.

Produces:

~~~go
const MaxReadBytes = 128 << 10

func ReadDefinition() llm.ToolDefinition

~~~

- [ ] **Step 1: Write failing reader tests**

Use `t.TempDir()` as root. Cover a valid `README.md`, malformed JSON, missing `path`, unknown JSON field, blank path, absolute path, `../outside.txt`, a directory, a 128 KiB + 1 byte file, and a symlink inside root pointing outside. Skip only the symlink case if the platform says symlink creation is unsupported. Assert exact content on success and only non-nil errors on failure.

- [ ] **Step 2: Run the focused test and verify it fails**

~~~powershell
go test ./internal/tool -run TestRead -count=1
~~~

Expected: package or symbol missing.

- [ ] **Step 3: Implement strict arguments and schema**

Decode raw arguments with `json.Decoder.DisallowUnknownFields()` into:

~~~go
type readArguments struct {
    Path string `json:"path"`
}
~~~

Reject blank paths. Return the schema from `ReadDefinition` with exactly one required relative `path` field and `additionalProperties:false`.

- [ ] **Step 4: Implement containment and bounded read**

Resolve root with `filepath.Abs` then `filepath.EvalSymlinks`. Reject `filepath.IsAbs(path)`. Join and resolve the target, use `filepath.Rel(resolvedRoot, resolvedTarget)` to reject `..` or an absolute relative path, and require `info.Mode().IsRegular()`. Read through `io.LimitReader(file, MaxReadBytes+1)`; return an error if the limit is exceeded.

## Task 3: Build the two-turn Agent Loop

**Files:**

- Create: `internal/agent/agent.go`

Produces:


- [ ] **Step 1: Write direct-answer and round-trip tests**

Create a test-local `scriptedClient` implementing `llm.Client`. It records each request, emits scripted events and returns scripted completions.

For a direct `stop` answer, assert one request with one tool definition and that buffered first-turn text is emitted only after the completion returns.

For a read round trip, create a temp `README.md`. Script first completion as `read_file` and second completion as final text. Assert two requests; request two is user, assistant tool call, matching `role:"tool"` result; its `Tools` slice is empty; only final text reaches `emitText`.

- [ ] **Step 2: Run the focused test and verify it fails**

~~~powershell

~~~

Expected: package or symbol missing.

- [ ] **Step 3: Implement `agent.Run`**

Create the first request with one user message and `Tools: []llm.ToolDefinition{tool.ReadDefinition()}`. Buffer first-turn text. On `stop`, emit it and return.

On `tool_calls`, require exactly one call named `read_file`. Append the provider assistant message, call `tool.Read(root, call.Arguments)`, then append a matching tool message. Convert read errors to text in the tool message:

~~~text
read_file failed: <safe error>
~~~

Make exactly one second request with the complete messages and no tools. Stream its text directly to `emitText` and require `stop`.

- [ ] **Step 4: Add rejected-state coverage**

Test malformed arguments and missing files as tool-result errors followed by a second request; multiple calls; an unknown tool; second-turn `tool_calls`; output callback failure; cancellation; and preserved `ReasoningContent` in the second request.
