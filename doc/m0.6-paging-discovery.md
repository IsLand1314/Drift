# M0.6：分页读取与 Discovery 目录忽略

状态：已实现。M0.6 在 M0.5 的 workspace 与 Focus 基础上，减少大型项目发现噪声，并为大文件提供按行分页读取能力。

## 1. 目标

M0.5 的 `list_files` 会递归发现 workspace 中的所有普通文件，大型仓库中的 Git 元数据、编辑器状态和依赖目录会占用模型上下文。M0.5 的 `read_file` 对超过 128 KiB 的文件只能报错，模型无法继续查看大文件的局部内容。

M0.6 只处理这两个问题：发现工具跳过固定的噪声目录，文件工具增加可控的行范围读取。它不改变写入能力、workspace 安全边界或 Agent Loop 预算。

## 2. `read_file` 分页契约

`path` 仍然是 workspace 内的相对文件路径，并新增两个可选整数：

```json
{"path":"internal/app/app.go","offset":0,"limit":100}
```

- `offset` 是 0-based 行偏移，默认 `0`；
- `limit` 是最多读取的行数，默认 `2000`；
- 只要传入 `offset` 或 `limit`，就进入分页模式；
- `offset < 0` 或 `limit <= 0` 会被拒绝；
- 分页结果仍不能超过单次 `128 KiB`；
- 页读取到文件末尾时返回剩余内容；还有下一页时追加：

```text
read_file: more lines available; next offset: 100
```

不传分页参数时保持兼容：128 KiB 以内的文件全文返回，超过限制时提示模型改用 `offset`/`limit`。分页读取不会绕过相对路径、符号链接、dotenv、目录和特殊文件校验。

### 2.1 参数由谁指定

`offset` 和 `limit` 是工具参数，不是用户每次运行都必须填写的命令行参数。当前 CLI 没有 `-offset` 或 `-limit` 选项；它们由 Agent 根据模型的工具调用决定。

通常流程是：

1. 用户只需要提供自然语言提示，例如 `解释 README.md`；
2. 模型调用 `read_file` 时，普通小文件通常省略 `offset` 和 `limit`，请求全文；
3. 如果文件超过 128 KiB，工具返回“请使用 `offset` 和 `limit` 分页”的受控错误；
4. 模型再次调用工具，先读取第一页，例如 `offset=0, limit=200`；
5. 如果结果中出现 `next offset`，模型可以把该值作为下一次调用的 `offset`，继续读取后续页面；
6. 最后一页没有 `next offset` 提示，模型可以停止读取并生成回答。

因此，用户一般不需要自己计算分页参数。用户只需在提示中表达范围要求，例如“只看前 100 行”或“解释第 200 行附近的代码”，模型可以据此生成合适的 `limit` 和 `offset`。最终参数仍由工具校验，模型不能绕过 workspace、dotenv、符号链接和文件大小边界。

参数含义示例：

```text
offset=0,   limit=100  -> 读取第 1～100 行
offset=100, limit=100  -> 读取第 101～200 行
offset=200, limit=100  -> 读取第 201～300 行
```

这里的 `offset` 是从 0 开始的行偏移，不是字节偏移；`limit` 是最多读取的行数，不是字节数。即使 `limit` 很大，单页结果仍不能超过 128 KiB；如果超过，工具会要求模型降低 `limit`。

用户也可以直接在提示中给出读取策略，但不能通过当前 CLI 直接传入 JSON：

```powershell
go run ./cmd/drift -p "读取 README.md 的前 80 行并总结"
go run ./cmd/drift -p "重点查看 internal/agent/agent.go 第 400 行附近"
```

这两种提示只是给模型范围建议，是否调用分页工具、具体使用什么 `offset` 和 `limit`，仍由 Agent Loop 执行模型返回的原生 `tool_calls` 决定。

## 3. Discovery 忽略目录

`list_files` 和 `search_text` 递归遍历时跳过以下目录名（大小写不敏感）：

```text
.git
.foxcode
.codex
.claude
.drift
node_modules
.venv
__pycache__
.tox
.mypy_cache
```

这些规则只用于 discovery，避免把工具运行数据、依赖和缓存送入模型。它们不改变 `read_file`：用户明确读取 workspace 内的普通文件时，仍按原有安全规则判断。符号链接目录仍然拒绝遍历，dotenv 文件仍然不会进入结果。

## 4. 调用流程

```text
Agent 返回 list_files/search_text
  -> walkRegularFilesContext
  -> 校验相对路径和 workspace
  -> 跳过 discoverySkipDirs
  -> 返回收敛后的发现结果

Agent 返回 read_file(path, offset, limit)
  -> 校验 JSON、相对路径、dotenv、符号链接和普通文件
  -> 无分页：小文件全文读取
  -> 有分页：Scanner 按行跳过 offset，读取 limit 行
  -> 页大小超过 128 KiB 时返回受控错误
  -> 有后续内容时提示 next offset
```

## 一句话概括

**FoxCode 是一个用 Go 编写的 Coding Agent Runtime（编码智能体运行时）**，面向本地真实代码仓库。它刻意强调自己**不是"把一次 LLM 请求包一层终端 UI"**的工具，而是一套完整的 Agent 执行基础设施：模型只负责决策，运行时负责其余工程问题——任务规划、流式事件、工具调度、上下文治理、长期记忆、权限控制、状态恢复与多 Agent 协作。

交互入口提供**终端 TUI** 和 **Remote Web UI** 两种，可接入 Anthropic、OpenAI、OpenAI 兼容接口以及 Codex（ChatGPT 登录态）四类 Provider；目前以源码构建为主要使用方式。

## 它想解决的工程问题

README 用一张对照表说明动机：

| 问题 | 做法 |
| --- | --- |
| MCP 工具变多后 Schema 反复挤占上下文 | 按 Schema 预算在 eager / native / dispatch 间自适应选择，并用 ToolSearch 按需发现工具 |
| 工具输出与长会话持续膨胀 | 工具结果预算 + 会话摘要两层治理，支持溢写、回读、配对保护和压缩边界恢复 |
| Agent 会改文件、执行命令 | 危险命令、路径沙箱、项目规则、权限模式、OS 沙箱、人工确认组成分层策略链 |
| 跨会话信息丢失或过时 | 四类型（`user`/`feedback`/`project`/`reference`）、双作用域（用户级 + 项目级）的文件化记忆，配合后台提取、整理与按需召回 |
| 跨文件任务需要拆分隔离 | 同步/异步子 Agent、Team 邮箱、共享任务状态、Git Worktree |

## 主要能力模块

- **多模型接入**：多 Provider 配置，启动时选择；Codex 走官方登录态且只读 `auth.json`，不委托官方 `codex exec`。
- **执行内核**：ReAct 风格流式工具调用循环，只读 Plan Mode、取消、限流退避、瞬态错误重试、max-token 续写恢复。只读工具可并发，写文件/命令保持串行，结果按模型原始调用顺序回填。
- **编码工具链**：文件读/写/编辑、Glob、Grep、Shell、任务与工具发现等。
- **上下文与会话**：溢写回读、摘要压缩、会话恢复、文件历史 rewind、输入队列去重。
- **扩展机制**：MCP（stdio / SSE / Streamable HTTP）、Skills、自定义斜杠命令、自定义 Agent、Hooks、项目指令文件（`FOXCODE.md` / `AGENTS.md` 等）。
- **多 Agent 协作**：子 Agent、后台任务、团队邮箱、tmux / iTerm2 外部队友进程。
- **隔离与权限**：多种权限模式、路径边界、规则文件、macOS/Linux OS 级沙箱、Git Worktree 隔离。
- **远程访问**：内置 HTTP + WebSocket Web UI，使用进程级配对 Token 并校验 Host / Origin。
